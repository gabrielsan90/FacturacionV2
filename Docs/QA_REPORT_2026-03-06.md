### BUG #1 — Contraseña visible como texto plano en el login
**Severidad:** 🔴 CRÍTICO
**Módulo:** Seguridad / Login (`/Auth/Login`)
**Tipo:** Seguridad — Exposición de credenciales

**Descripción:**
El campo de contraseña en la página de login renderiza con `type="text"` visible bajo ciertas condiciones, exponiendo la contraseña en pantalla durante el proceso de autenticación.

**Pasos para reproducir:**
1. Navegar a `http://127.0.0.1:5207/Auth/Login`
2. Escribir una contraseña en el campo `#txtPassword`
3. Observar que los caracteres son visibles sin enmascarar

**Comportamiento esperado:** `input[type="password"]` — caracteres enmascarados con `•••`
**Comportamiento actual:** `input[type="text"]` — contraseña expuesta en texto plano

**Impacto:**
- Usuario mirando por encima del hombro (shoulder surfing) puede leer la contraseña
- Contraseña puede aparecer en capturas de pantalla accidentales

**Fix sugerido:**
```html
<!-- Cambiar -->
<input type="text" id="txtPassword" ...>
<!-- Por -->
<input type="password" id="txtPassword" autocomplete="current-password" ...>
```

### BUG #2 — Sin `appsettings.Development.json`: ambiente local llama a API de producción
**Severidad:** 🔴 CRÍTICO
**Módulo:** Infraestructura / Configuración
**Tipo:** Configuración — Contaminación de datos

**Descripción:**
No existe `appsettings.Development.json` para el Frontend. Tanto `appsettings.json` como `appsettings.Production.json` apuntan a `https://api.invoicingcr.com`. Cualquier prueba local que cree, modifique o elimine datos opera sobre **la base de datos de producción**.

**Evidencia:**
```json
// appsettings.json (sin override de Development)
{
  "ApiBaseUrl": "https://api.invoicingcr.com"
  //"ApiBaseUrl": "https://localhost:7501"  ← Comentado
}

// appsettings.Production.json
{
  "ApiBaseUrl": "https://api.invoicingcr.com"
}
// FALTA: appsettings.Development.json con ApiBaseUrl local
```

**Comportamiento esperado:** Ambiente Development → `http://localhost:5193`
**Comportamiento actual:** Development → `https://api.invoicingcr.com` (producción)

**Impacto:**
- Todas las pruebas CRUD durante esta sesión de QA operaron sobre producción
- Clientes, productos, proveedores, asientos contables de prueba pueden existir en la BD de producción
- Un desarrollador podría corromper datos reales sin saberlo

**Fix sugerido:**
Crear `Facturacion.Frontend/appsettings.Development.json`:
```json
{
  "Logging": {
    "LogLevel": {
      "Default": "Debug",
      "Microsoft.AspNetCore": "Information"
    }
  },
  "ApiBaseUrl": "http://localhost:5193"
}
```

### BUG #18 — Cookie `authToken` accesible vía JavaScript (sin flag HttpOnly)
**Severidad:** 🔴 CRÍTICO
**Módulo:** Seguridad / Autenticación
**Tipo:** Seguridad — XSS Token Theft

**Descripción:**
La cookie `authToken` que contiene el JWT de autenticación es accesible desde JavaScript mediante `document.cookie`. Sin el flag `HttpOnly`, cualquier script malicioso inyectado en la página puede robar el token de sesión.

**Evidencia:**
```javascript
// Ejecutado en consola del navegador:
document.cookie
// Resultado: "authToken=eyJhbGci..." (JWT completo visible)
```

**Comportamiento esperado:** Cookie con `HttpOnly=true` — invisible para `document.cookie`
**Comportamiento actual:** Cookie accesible via JS — vulnerable a XSS token theft

**Impacto:**
- Cualquier XSS en la aplicación permite robar sesiones activas
- Atacante puede hacer peticiones autenticadas en nombre del usuario
- OWASP Top 10: A07:2021 – Identification and Authentication Failures

**Fix sugerido:**
En `Program.cs` del Backend, al generar la cookie de autenticación:
```csharp
// En Facturacion.Frontend/Program.cs
builder.Services.ConfigureApplicationCookie(options => {
    options.Cookie.HttpOnly = true;       // ← Agregar
    options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
    options.Cookie.SameSite = SameSiteMode.Strict;
});

// O en el controller donde se crea la cookie authToken:
Response.Cookies.Append("authToken", token, new CookieOptions {
    HttpOnly = true,       // ← CRÍTICO
    Secure = true,
    SameSite = SameSiteMode.Strict,
    Expires = DateTimeOffset.UtcNow.AddHours(8)
});
```

### BUG #3 — Validación de email no muestra mensaje de error específico
**Severidad:** 🟡 MEDIO
**Módulo:** Ventas / Clientes (`/Ventas/Clientes`)
**Tipo:** UX / Validación de formulario

**Descripción:**
Al ingresar un email con formato inválido (ej: `"notanemail"`), el campo dispara `typeMismatch` de HTML5 pero el `invalid-feedback` asociado no muestra el mensaje de error. El campo se marca con borde rojo pero el usuario no sabe qué está mal.

1. Abrir modal "Nuevo Cliente"
2. Escribir `notanemail` en el campo Email

function saveRecord() {

    $.ajax({
        // ...
        complete: function() {
            btn.prop('disabled', false).html('<i class="bi bi-check-lg me-1"></i>Guardar');
        }
    });
}

### BUG #10 — Errores de ModelState se disparan como SweetAlert en recargas de página
**Severidad:** 🟡 MEDIO
**Módulo:** Autenticación / Login (y potencialmente otros formularios con server-side validation)
**Tipo:** UX — Experiencia degradada tras recarga

**Descripción:**
Los errores de validación del servidor (ModelState) se inyectan como código JavaScript hardcodeado en el HTML de respuesta. Al recargar la página (F5 o navegación Back/Forward), esos mensajes de error vuelven a dispararse como alertas SweetAlert aunque el error ya no sea relevante.

**Pasos para reproducir:**
1. Enviar el formulario de login con datos inválidos
2. El servidor devuelve la página con error en ModelState
3. Aparece SweetAlert con el error (comportamiento correcto)
4. Presionar F5 para recargar la página
5. La alerta de error vuelve a aparecer sola

**Comportamiento esperado:** Al recargar, la página muestra limpia sin alertas previas
**Comportamiento actual:** El JS hardcodeado en el HTML vuelve a ejecutar el Swal en cada carga

**Fix sugerido:**
Usar el patrón PRG (Post-Redirect-Get) con `TempData` en lugar de inyectar errores como JS:
```csharp
// En el PageModel:
TempData["Error"] = "Credenciales inválidas";
return RedirectToPage();

// En el .cshtml:
@if (TempData["Error"] != null) {
    <script>Swal.fire('Error', '@TempData["Error"]', 'error');</script>
}
```

### BUG #13 — Botón Guardar habilitado cuando Debe ≠ Haber en Asientos Contables
**Severidad:** 🟡 MEDIO
**Módulo:** Contabilidad / Asientos Contables
**Tipo:** Validación client-side — Experiencia de usuario

**Descripción:**
La validación client-side de balance en Asientos Contables tiene una condición incompleta: el botón "Guardar" solo se deshabilita cuando ambos totales son `0`. Cuando hay movimientos con Debe ≠ Haber (desbalanceado pero con valores), el botón permanece habilitado, permitiendo enviar el formulario para que el servidor lo rechace en lugar de prevenirlo en el cliente.

**Evidencia del código problemático:**
```javascript
// Lógica actual en updateTotals():
if (totalDebe === 0 && totalHaber === 0) {
    $('#btnGuardar').prop('disabled', true);  // Solo deshabilita si ambos son 0
} else {
    $('#btnGuardar').prop('disabled', false);  // ← BUG: habilitado aunque desbalanceado
}
```

**Comportamiento esperado:** Botón deshabilitado siempre que `totalDebe !== totalHaber`
**Comportamiento actual:** Botón habilitado si hay al menos un valor (aunque esté desbalanceado)

**Nota:** El servidor **sí** rechaza asientos desbalanceados correctamente. El bug es solo a nivel de UX — se hace un round-trip innecesario al servidor.

**Fix sugerido:**
```javascript
if (diferencia === 0 && totalDebe > 0) {
    $('#btnGuardar').prop('disabled', false);  // ← Balanceado y con valores
} else {
    $('#btnGuardar').prop('disabled', true);   // ← Deshabilitado en cualquier otro caso
}
```

### BUG #14 — Mensajes de error muestran JSON crudo en SweetAlert
**Severidad:** 🟡 MEDIO
**Módulo:** Contabilidad / Asientos Contables (y potencialmente otros módulos)
**Tipo:** UX — Mensajes de error no amigables

**Descripción:**
Cuando el servidor devuelve un error en formato `ActionResponse<T>`, el código JavaScript verifica `response.success` (campo incorrecto) en lugar de `response.wasSuccess`. Esto provoca que el mensaje de error no se extraiga correctamente y se muestre el objeto JSON completo en la alerta de error.

**Evidencia:**
```javascript
// Código actual (problemático):
success: function(response) {
    if (response.success) { ... }           // ← Campo incorrecto
    else { showError(response.message); }   // ← Si response.message es undefined,
                                             //   muestra "[object Object]" o JSON raw
}
```

**Estructura real del ActionResponse:**
```json
{ "wasSuccess": false, "message": "El asiento no está balanceado. Diferencia: 500.00" }
```

**Comportamiento esperado:** SweetAlert muestra: `"El asiento no está balanceado. Diferencia: 500.00"`
**Comportamiento actual:** SweetAlert muestra JSON crudo o mensaje genérico

**Fix sugerido:**
```javascript
success: function(response) {
    if (response.wasSuccess) {  // ← Corregir nombre del campo
        Swal.fire('Éxito', response.message || 'Operación exitosa', 'success');
        // ...
    } else {
        Swal.fire('Error', response.message || 'Error desconocido al procesar la solicitud', 'error');
    }
}
```
**Recomendación adicional:** Auditar todos los archivos `.cshtml` del Frontend para verificar que usen `wasSuccess` consistentemente.

### BUG #17 — Sin encabezado Content-Security-Policy (CSP)
**Severidad:** 🟡 MEDIO
**Módulo:** Infraestructura / Seguridad HTTP
**Tipo:** Seguridad — Defensa en profundidad

**Descripción:**
Las respuestas HTTP del Frontend no incluyen el encabezado `Content-Security-Policy`. Combinado con BUG #18 (cookie authToken no HttpOnly), la ausencia de CSP amplifica significativamente la superficie de ataque ante inyecciones XSS.

**Evidencia:**
```javascript
// Verificado en consola:
document.querySelector('meta[http-equiv="Content-Security-Policy"]')  // null
// Headers HTTP inspeccionados: no contiene Content-Security-Policy
```

**Comportamiento esperado:** Encabezado CSP restrictivo en todas las respuestas HTTP
**Comportamiento actual:** Sin CSP — scripts de cualquier origen pueden ejecutarse

**Fix sugerido:**
```csharp
// En Program.cs del Frontend:
app.Use(async (context, next) => {
    context.Response.Headers.Add("Content-Security-Policy",
        "default-src 'self'; " +
        "script-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net; " +
        "style-src 'self' 'unsafe-inline' https://cdn.jsdelivr.net; " +
        "img-src 'self' data: https:; " +
        "connect-src 'self' https://api.invoicingcr.com; " +
        "font-src 'self' https://cdn.jsdelivr.net; " +
        "frame-ancestors 'none';"
    );
    await next();
});

// También agregar:
context.Response.Headers.Add("X-Content-Type-Options", "nosniff");
context.Response.Headers.Add("X-Frame-Options", "DENY");
context.Response.Headers.Add("Referrer-Policy", "strict-origin-when-cross-origin");
```

### BUG #16 — Navegador redirigido a URL del Backend API durante pruebas de RRHH
**Severidad:** 🟢 BAJO
**Módulo:** RRHH / Puestos (posiblemente una acción de formulario incorrecta)
**Tipo:** Funcional — Redirección incorrecta

**Descripción:**
Durante las pruebas en el módulo RRHH > Puestos, el navegador fue redirigido a `http://127.0.0.1:5193` (la URL del Backend API) en lugar de permanecer en el Frontend (puerto 5207). Esto causó que el usuario viera JSON crudo de la API en lugar del UI de la aplicación.

**Posibles causas:**
- Un `<form action="...">` con URL absoluta apuntando al backend
- Una redirección JavaScript con `window.location.href` usando la URL del backend
- Un `href` en un enlace apuntando directamente a la API
